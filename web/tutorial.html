How PiPi works

The idea in one minute

Imagine that useful information is spread across many places: sensor systems, CSV files, university documents, websites and GitHub repositories. PiPi gives these sources one common catalog and one search layer.

PiPi does not need to copy every original source into one giant database. It records what a source is, where it comes from, how it can be accessed and which version was used. For searchable text, PiPi creates small text chunks and a search index.

The important part: PiPi also remembers how information was searched. A different retrieval method can return different evidence even when the data and the question are unchanged. That search configuration is therefore part of the provenance.

What happens from source to answer?

1. Discover. PiPi finds or registers a data source, for example a sensor dataset, PDF, CSV or GitHub repository.

2. Describe. The catalog stores metadata such as title, source, type, access information and version.

3. Index. Text-based content is split into smaller chunks. These chunks can be searched by exact words and, when vectors are available, by meaning.

4. Retrieve. A retrieval profile decides how PiPi searches. The profile is frozen and has its own configuration hash.

5. Record. Every search can be stored as a retrieval run with the query, selected profile, data snapshot and returned evidence. Later we can compare or replay runs.

Think of it like a laboratory experiment. The data are the material, the retrieval profile is the experimental procedure, and the returned chunks are the observed result. If the procedure changes, we must record that change.

How to search

Open Search indexed content, type a question or a few keywords, choose a retrieval profile and press Search indexed content.

For example, try temperature demo-site-b, runtime ownership or rodna ravnopravnost studenata.

The result cards show the matching source text. Technical labels such as lexical #, vector # and cos tell us why a result was ranked highly.

What do the retrieval profiles mean?

Lexical baseline · v1 searches mostly by matching words. It is simple and strong when the question uses the same words as the source.

Vector E5 · content-v1 searches by meaning using multilingual E5 embeddings. It can connect related wording even when exact words differ.

Hybrid E5 · content-v1 combines lexical and vector search. This is the stable default baseline.

Vector/Hybrid E5 · metadata-v1 also puts dataset title and source path into the vector representation. This can help some questions and hurt others. That is exactly why PiPi keeps it as a separate profile instead of replacing the baseline.

Vectors 1487/1487 means every currently searchable chunk has a vector for that selected profile. If a profile shows 0/1487, use Build/update selected vectors once.

Why keep several versions?

Suppose the same question gives result A with one profile and result B with another. If we only keep the newest configuration, we lose the ability to explain the difference.

PiPi therefore keeps retrieval profiles side by side. The data may stay identical while the retrieval procedure changes. This lets us measure retrieval drift: how much the selected evidence changes because of the retrieval configuration itself.

Later, when a language model generates an answer from that evidence, we can separate three causes of change: data drift, retrieval drift and generation drift.

Why are we building this?

Most RAG systems focus on getting a good answer now. PiPi is also interested in a harder question: can we explain and reproduce why the system used exactly this evidence?

That matters in research, public institutions, industry and any system where data change over time. Knowing the source document is not enough if the retrieval process that selected it has changed.

Project point: treat retrieval configuration as part of provenance. PiPi is a working Data Space platform for testing that idea on heterogeneous, versioned data.
