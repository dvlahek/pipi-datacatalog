1. Ideja projekta u jednoj minuti

Zamisli da su korisne informacije razbacane po mnogo mjesta: senzori, CSV datoteke, fakultetski dokumenti, web stranice i GitHub repozitoriji. PiPi im daje zajednički katalog i zajednički način pretraživanja.

PiPi ne mora sve originalne podatke preseliti u jednu ogromnu bazu. Pamti što je izvor, gdje se nalazi, tko ga objavljuje, kako mu se pristupa i koja je verzija korištena. Za tekst koji želimo pretraživati PiPi radi manje dijelove teksta, odnosno chunkove, i gradi indeks.

1. Izvor
2. Katalog i metadata
3. Chunkovi i vektori
4. Retrieval profil
5. Dokaz / rezultat
Glavna ideja: nije dovoljno znati samo iz kojeg je dokumenta informacija došla. Važno je znati i kako je sustav baš taj dokaz pronašao. Zato PiPi tretira retrieval konfiguraciju kao dio provenancea, odnosno podrijetla rezultata.

2. Kako dodati novi izvor

Postoje dva osnovna načina. Provider-managed izvore PiPi pronalazi automatski kroz Sync providers. To su, primjerice, Sensor Hub i FOI dokumenti. Registered resources su izvori koje korisnik ručno dodaje URL-om, primjerice GitHub repozitorij, javni CSV, JSON, PDF ili web resurs.

Korak A — otvori “Add resource”

U polje Resource URL zalijepi javni URL izvora. Za Type je najjednostavnije ostaviti Auto detect.

Korak B — opiši izvor

Po želji dodaj naziv, publisher, licencu i keywords. Access level i Commercial terms opisuju uvjete korištenja izvora.

Korak C — klikni “Analyze and add”

PiPi provjeri URL, prepozna vrstu izvora, zabilježi metadata i provenance te ga doda u katalog. Izvor se zatim vidi u tablici Registered resources.

Korak D — indeksiraj izvor ako želiš pretraživati sadržaj

Katalogizacija i RAG indeksiranje nisu isto. Izvor može biti u katalogu, a da njegov sadržaj još nije indeksiran. Za tekstualne izvore koristi akciju Index. Nakon toga dobivamo chunkove koje retrieval može koristiti.

Primjer 1 — GitHub repozitorijMožeš dodati javni repozitorij REA:https://github.com/morluto/reaType može ostati Auto detect ili se ručno postaviti na GitHub repository. Nakon indeksiranja PiPi pretražuje dopuštene tekstualne datoteke repozitorija i pamti putanju datoteke, npr. docs/web-runtime.md.
Primjer 2 — javni CSVZa test može se koristiti javna CSV datoteka iz PiPi repozitorija:https://raw.githubusercontent.com/dvlahek/pipi-datacatalog/feature/sensor-hub-bootstrap/data/csv/pipi_demo_environment.csvNakon indeksiranja svaki red može postati mali pretraživi zapis, pa upit temperature demo-site-b može pronaći vrijednost temperature za tu lokaciju.
Primjer 3 — PDF ili dokumentZalijepi javni HTTPS URL dokumenta i ostavi Auto detect. Ako je tekst moguće izvući, PiPi ga može podijeliti u chunkove i indeksirati. Trenutačni osnovni pipeline ne koristi OCR za skenirane slike bez ugrađenog teksta.
Važno: oznaka “private” u ovom MVP-u je metadata o pravilima dijeljenja. Ako je originalni URL javno dostupan na internetu, PiPi ga time ne može učiniti privatnim. Izvor ostaje pod kontrolom izvornog sustava.

4. Kako pretraživati

Search catalog pretražuje opisne podatke kataloga. Koristi ga kada tražiš dataset prema nazivu, tipu, publisheru ili ključnim riječima.

Search indexed content pretražuje stvarni indeksirani tekst. Upiši pitanje ili nekoliko riječi, odaberi retrieval profil i klikni Search indexed content.

Primjeri upita:

  • temperature demo-site-b — konkretna vrijednost u CSV-u
  • vlaga na demo-site-a — hrvatski semantički upit nad istim CSV-om
  • runtime ownership — tehnička tema u GitHub repozitoriju
  • rodna ravnopravnost studenata — sadržaj FOI dokumenta

Rezultati mogu pokazivati oznake lexical #, vector # i cos. One pomažu objasniti zašto je rezultat visoko rangiran.

5. Što znače retrieval profili?

Lexical baseline · v1 traži uglavnom podudaranje riječi. Dobar je kada upit koristi iste riječi kao izvor.

Vector E5 · content-v1 traži po značenju koristeći multilingual E5 embeddinge.

Hybrid E5 · content-v1 kombinira lexical i vector retrieval. To je naš stabilni default baseline.

Vector/Hybrid E5 · metadata-v1 u vektorsku reprezentaciju dodaje i naslov dataseta te putanju izvora. To nekim upitima pomaže, a nekima odmaže, zato se profil čuva odvojeno.

Primjer: isti podaci, isti E5 model i isti upit mogu dati drukčiji poredak samo zato što je promijenjen retrieval profil. PiPi zato ne prepisuje staru verziju nego obje čuva paralelno s vlastitim configuration hashom.

Vectors 1487/1487 znači da svih 1487 trenutačno pretraživih chunkova ima embedding za odabranu vektorsku reprezentaciju. Lexical profil ne treba vektore.

6. Zašto je ovo više od običnog searcha?

Većina RAG sustava želi samo pronaći dobar kontekst i dati odgovor. PiPi želi moći odgovoriti i na drugo pitanje: zašto je sustav izabrao baš ovaj dokaz i možemo li to kasnije reproducirati?

Svaki zamrznuti retrieval profil ima svoj identitet i configuration hash. Pretrage se mogu zapisivati kao retrieval runs zajedno s upitom, profilom, snapshotom kataloga i vraćenim dokazima.

Kasnije možemo razlikovati tri razloga promjene odgovora:

  • data drift — promijenili su se podaci
  • retrieval drift — promijenio se način pronalaska dokaza
  • generation drift — promijenio se generativni model ili njegova konfiguracija
Poanta PiPi projekta: izgraditi Data Space u kojem su heterogeni izvori katalogizirani, verzionirani i pretraživi, ali i u kojem je AI retrieval dovoljno transparentan da možemo pratiti, usporediti i reproducirati put od izvora do dokaza, a kasnije i do LLM odgovora.
Idea Add sources Indexing Search Profiles Why it matters

1. The project idea in one minute

Imagine useful information spread across many places: sensor systems, CSV files, university documents, websites and GitHub repositories. PiPi gives these sources a shared catalog and a shared search layer.

PiPi does not need to move every original dataset into one giant database. It records what a source is, where it comes from, who publishes it, how it can be accessed and which version was used. Searchable text is split into smaller pieces called chunks and indexed.

1. Source
2. Catalog and metadata
3. Chunks and vectors
4. Retrieval profile
5. Evidence / result
Main idea: knowing the source document is not enough. We also need to know how the system selected that evidence. PiPi therefore treats retrieval configuration as part of provenance.

2. How to add a new source

There are two main paths. Provider-managed sources are discovered by PiPi through Sync providers, for example Sensor Hub and FOI documents. Registered resources are sources a user adds manually by URL, such as a GitHub repository, public CSV, JSON, PDF or web resource.

Step A — open “Add resource”

Paste a public URL into Resource URL. The easiest choice for Type is Auto detect.

Step B — describe the source

Optionally add a name, publisher, license and keywords. Access level and Commercial terms describe the intended usage conditions.

Step C — click “Analyze and add”

PiPi validates the URL, detects the source type, records metadata and provenance, and adds it to the catalog. The source then appears under Registered resources.

Step D — index it if you want to search its content

Catalog registration and RAG indexing are different. A source can exist in the catalog without its content being searchable. For text-based sources use the Index action. PiPi then creates searchable chunks.

Example 1 — GitHub repositoryAdd the public REA repository:https://github.com/morluto/reaKeep Auto detect or choose GitHub repository. After indexing, PiPi searches allowed text files and keeps source paths such as docs/web-runtime.md.
Example 2 — public CSVA simple test source is the public PiPi demo CSV:https://raw.githubusercontent.com/dvlahek/pipi-datacatalog/feature/sensor-hub-bootstrap/data/csv/pipi_demo_environment.csvAfter indexing, rows become small searchable records. A query such as temperature demo-site-b can retrieve the matching temperature row.
Example 3 — PDF or documentPaste a public HTTPS document URL and keep Auto detect. If text can be extracted, PiPi can chunk and index it. The current basic pipeline does not use OCR for image-only scans without embedded text.
Important: in this MVP, “private” is sharing metadata. If the original source URL is publicly reachable on the internet, PiPi cannot make that external URL private. The original system remains authoritative.

Rule of thumb: the catalog says “what the source is”, the index says “which content can be searched”, and vectors say “how a semantic retrieval profile represents that content”.

4. How to search

Search catalog searches descriptive catalog metadata. Use it to find datasets by title, type, publisher or keywords.

Search indexed content searches the indexed source text. Type a question or a few words, choose a retrieval profile and press Search indexed content.

Example queries:

  • temperature demo-site-b — exact information in a CSV
  • vlaga na demo-site-a — a Croatian semantic query over the same CSV
  • runtime ownership — a technical topic in a GitHub repository
  • rodna ravnopravnost studenata — content from an FOI document

Results may show lexical #, vector # and cos. These labels help explain why a result ranked highly.

5. What do retrieval profiles mean?

Lexical baseline · v1 mainly matches words. It is strong when the query uses the same wording as the source.

Vector E5 · content-v1 searches by meaning using multilingual E5 embeddings.

Hybrid E5 · content-v1 combines lexical and vector retrieval. This is the stable default baseline.

Vector/Hybrid E5 · metadata-v1 also includes dataset title and source path in the vector representation. This helps some queries and hurts others, so it is stored as a separate profile.

Example: the same data, same E5 model and same query can produce a different ranking only because the retrieval profile changed. PiPi therefore keeps profiles side by side, each with its own configuration hash.

Vectors 1487/1487 means all 1487 currently searchable chunks have an embedding for the selected vector representation. A lexical-only profile does not need vectors.

6. Why is this more than ordinary search?

Most RAG systems focus on finding good context and producing an answer. PiPi also asks a harder question: why did the system select exactly this evidence, and can we reproduce that selection later?

Each frozen retrieval profile has its own identity and configuration hash. Searches can be recorded as retrieval runs together with the query, profile, catalog snapshot and returned evidence.

Later we can separate three causes of change:

  • data drift — the data changed
  • retrieval drift — the evidence-selection procedure changed
  • generation drift — the generative model or generation configuration changed
PiPi project point: build a Data Space where heterogeneous sources are cataloged, versioned and searchable, while AI retrieval remains transparent enough to trace, compare and reproduce the path from source to evidence and, later, to an LLM answer.
